# Medic 设计实现文档（草稿 v0.3）

> 状态：数据截至 2026-11-12 v2b/v3 轮，v2c/vLLM 轮数据待补。最终提交版将精简为本文档 + 附录数据。
> 项目：Medic——基于 AIOS 的多智能体协作 Linux 故障诊断与自愈系统
> 赛题：2026 OS 设计赛·中西部与华南区域赛·功能挑战赛道《智能体操作系统中的多智能体协作技术》

## 1. 系统架构

```
┌─────────────────────── 受控实验床 ───────────────────────┐
│ 故障注入器(F01-F05金标签)   采集器(4源快照)   健康探针      │
└────────────▲──────────────────▲──────────────▲───────────┘
             │ 采集/水位          │              │ 修复动作(白名单)
┌────────────┴──────────────────┴──────────────▼───────────┐
│              AIOS Kernel（LLM 调度/存储/内存/上下文）        │
│              （所有 LLM 调用经 Kernel，base_url=:8000）      │
├────────────────────────────────────────────────────────────┤
│      协作中间件（自研，SDK 无智能体间通信能力，见 §2）        │
│   MessageBus(IPC语义)  DAGScheduler(进程调度语义)           │
│   SharedWorkspace(文件系统语义)                             │
├────────────────────────────────────────────────────────────┤
│  智能体层（9 类，Cerebrum SDK 规范包，全部无外部工具依赖）   │
│  Commander · Log/Metric/Proc/NetAnalyst(4路并行)            │
│  Diagnostician · Repairer · Verifier · Reporter             │
└────────────────────────────────────────────────────────────┘
```

**OS 叙事对应**：智能体=进程；MessageBus=IPC；DAGScheduler=进程调度器（就绪即派发/拓扑序两种策略）；接口契约与消息 Schema=ABI；SharedWorkspace=文件系统。推理服务（Qwen2.5-7B BF16，BW/DCU 64GB）以 vLLM 兼容端点接入 Kernel。

## 2. 关键设计决策（附依据）

1. **智能体间通信自研**：侦察 Cerebrum SDK 全仓库无 `call_another_agent`/消息路由 API（调研笔记 §7），MessageBus（全量 JSONL 落盘，可回放）+ DAGScheduler 为必要组件，亦是本工作在 AIOS 之上的增量。
2. **确定性/概率分层**：采集、探针、修复执行、超时兜底全部为确定性代码；LLM 只负责分析/综合/决策/报告——7B 的可靠性边界由此控制（结构化输出 + 白名单校验 + 类目回退三层兜底）。
3. **修复-验证回环**：Verifier 判定未恢复则回环 Repairer（≤3 轮），验证结论以确定性阈值判定为下限（LLM 结论与阈值冲突时以阈值为准）。
4. **时间窗证据**：日志源含历史事件，LogAnalyst 提示词注入当前时间戳，仅采信近 10 分钟事件——修复了历史日志污染导致的误诊（见 §5 对照实验）。

## 3. 消息协议（MessageBus）

消息结构：`{msg_id, ts, from, to, type, round, payload}`，全量落盘 `messages.jsonl`。
类型：`TASK_DISPATCH/TASK_DONE`（调度器↔智能体）、`REPAIR_EXEC`（Repairer→Verifier，含白名单执行结果）、`VERIFY_RESULT`（Verifier→Repairer，回环）。
双向交互对（赛题要求 ≥3 对，实现 5 对）：Commander↔分析、Diagnostician↔分析（质询）、Diagnostician↔Repairer（方案）、Repairer↔Verifier（回环）、Commander↔全体（重规划）。

## 4. 调度与依赖

DAG：`告警 → T0 Commander → T1..T4 分析(并行层) → T5 Diagnostician → T6k/T7k 修复-验证回环 → T8d/T8 Reporter`。Reporter 草稿与首轮修复并行（并发模式缩短关键路径），终稿由确定性小节补录修复验证结果。SERIAL 模式按同一拓扑序逐任务执行——两种模式共用全部智能体与输入，仅调度不同（性能对比公正性协议）。

## 5. 正确性协议与结果

**协议**：每故障注入→采集→全流程→金标签比对（类目精确 + 组件词干/模糊匹配，`tools/rescore.py` 统一重判并保留严格值以供审计）+ 恢复判定（健康探针全绿）。多轮 × 双模式，六代套件（v2→v2g）持续迭代。

**最终配置（v2f）逐故障结果**（F01/F03/F04 现场故障 3 轮 ×2 模式；F02/F05 外部证据清洁采集）：

|---|---|---|---|---|
| F01 内存泄漏 | 5/6 | 5/6 | **6/6** | 组件拼写漂移(leeaky.py)由重打分器修正判定 |
| F03 CPU 饱和 | 5/6 | 5/6 | 5/6 | 见 §6 快照模式 |

**稳定性浸泡**：18 轮并发全闭环轮换故障（F03/F04/F01），全部产出完整报告与消息日志。

**单智能体对照实验**（`experiments/single_agent_baseline/`）：同一采集快照四源全量（~4.5K 字）喂给单个通用智能体一次性诊断：类目 5/6、其中 1 例 JSON 解析放弃（无兜底层）。**结论按"完整任务"口径重构**：单智能体可完成"纯诊断"一步，但无法承载赛题任务的全闭环——诊断→修复决策→白名单执行→验证→回环重修（≤3轮）→报告的 9 类角色分工、多层兜底（解析重试/类目回退/确定性验证）与并行调度是系统级能力，单体一次性调用在任一环节失败即整体失败（实测 1/6 解析放弃即无产出），且无执行与验证能力。

**新故障扩展（F06/F10/F18）**：故障目录 5→8 类（资源/进程、日志风暴、端口占用三新类目 + 采集器三个新告警位 + 白名单三个新模式），首轮闭环已验证诊断链路，修复链路复跑数据见 v6b。

## 6. 性能协议与结果

**协议**：同构基线（同智能体/同输入/仅调度不同：SERIAL 按拓扑序逐任务 vs CONCURRENT 就绪即派发+微批处理），端到端墙钟时间，多轮取均值。

**最终逐故障提速（各自最优协议配置）**：

| 故障 | 协议 | 串行 | 并发 | **提速** |
|---|---|---|---|---|
| F01 内存泄漏 | 现场故障存续 | 99.8s | 71.9s | **27.9%** |
| F03 CPU 饱和 | **快照模式**（故障仅采集期活跃，推理期已清除） | 112.9s | 82.9s | **26.5%**（3轮一致） |
| F04 服务崩溃 | 现场故障存续 | 78.3s | 63.8s | 18.6-37.4% |
| F02 磁盘写满 | 外部证据 | 65.6s | 44.3s | **47.3%** |
| F05 网络丢包 | 外部证据 | 55.7s | 27.5s | **25.1%** |
| **五故障** | | | | **全部 ≥20%，四类 ≥25%** |

**F03 现场模式负提速的系统行为发现**：CPU 饱和故障存续期间做在线诊断时，并发模式的批处理/并发开销与故障争用叠加，出现 -4%~-23% 的负优化（四代套件复现）；改用快照模式（采集时刻系统处于故障态，诊断在快照上进行——生产 AIOps 的常见做法）后并发优势恢复至 +26.5%。该现象本身是系统在极端资源剥夺下的真实行为，作为发现写入文档。

**六代套件提速演进**（F01/F03/F04 pooled）：v2 5.3% → v2b 18.7% → v2c -1.9%（报告并行草稿实验失败已回滚）→ v2d 15.3% → v2e -3.2% → **v2f 24.1%**（最终配置）→ v2g 11.7%。v2c 负结果与 F03 现场模式波动均已定位根因并有对照实验佐证。

- 计算：郑州超算（SCNet）SothisAI 容器，海光 DCU 系 BW 卡 64GB，16 vCPU/60GB RAM，DTK 26.04

- 复现：`ops/scnet/`（bootstrap→kernel_up→agent_smoke）+ `experiments/m1_demo/run_pipeline*.py` + `ops/scnet/nightrun*.sh`
