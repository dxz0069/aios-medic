## 1. 赛题本体深度分析：200 分怎么构成的

评分原文（赛题原文与 GitLink 赛题页一致，https://www.gitlink.org.cn/OSKYCX/zntczxtzddzntxzjs ）：

| 板块 | 分值 | 子项 |
|---|---|---|
| 功能完整性 50% | 100 | 复杂任务合理、满足任务场景要求 **40**；多智能体实现及协作流程设计 **60** |
| 应用效果 50% | 100 | 并发比串行总时间减少 ≥20% **50**；多智能体正确完成任务 **50** |

【事实】四条硬性要求：①≥4 种可协作智能体；②任务可分解为≥4 个**可并行**子任务且**自动分配**；③≥3 对不同类型智能体**双向交互**；④满足先后顺序与依赖约束。

### 1.1 逐项得分策略

**60 分"多智能体实现及协作流程"（最大单项，判据最客观）**
- 【判断】评审大概率逐条对照①—④。策略：每条要求都要有"可指认"的证据——智能体种类清单（代码里的 6 个包）、并行调度时间线图（甘特图）、双向消息流图（谁给谁发了什么、几轮）、DAG 依赖图（含回环）。文档按评分点写自查表，让评委 30 秒内能对号入座。
- ④"自动分配"容易被忽略：必须展示调度器按子任务类型路由到智能体的代码逻辑与日志，不能是写死的脚本顺序。

**40 分"任务场景合理"**
- 【判断】"合理"可拆三个判据：(a) 单智能体确实做不了——最好有**单智能体对照实验**（把整个任务一次性丢给一个 agent，展示其输出超长/遗漏/失败，与我们系统的成功结果对比）；(b) 有现实意义；(c) 分解与依赖是场景内在的，不是生造的。
- 【事实】赛题只要求"自行拟定单智能体无法完成的复杂任务"，**无领域限制**；背景里交通/能源/物流/智能家居城市工厂只是多智能体应用举例，不是命题范围。

**50 分提速 ≥20%**
- 【事实】AIOS 论文的 2.1× 出处（ar5iv 全文，https://ar5iv.labs.arxiv.org/html/2403.16971 ）：并发 serving 加速——最多 250 并发线程、默认 Round Robin 调度、单张 RTX A5000 24GB、Llama-3.1-8B、HumanEval 基准 + Reflexion 智能体；指标是吞吐与平均等待时间。论文**没有**"串行流水线 vs 并发流水线"的端到端对比——那是赛题为我们定制的更宽松指标。
- 【判断】两个陷阱：(a) 串行基线的公正性——基线必须与并发版同构（同智能体、同提示词、同参数，仅调度顺序不同），协议写进文档可复现，否则评审可质疑刷分；(b) 提速来源要讲清楚——单 GPU 上真加速来自 vLLM continuous batching（多个 7B 请求合并批处理）+ 非 LLM 任务（跑测试/采集命令/文件 IO）与 LLM 调用的时间重叠。设计上让"可并行层"占端到端时间 ≥60%。
- 【事实】论文硬件先例就是单卡 24GB 跑 8B（Llama-3.1-8B / Mistral-7B，Ubuntu 22.04），与赛题"7B/8B 端侧"完全一致——我们的硬件方案没有风险溢价。

**50 分正确性**
- 【判断】唯一稳的拿法是**机器可判的验收**：pytest 通过率 / 故障定位准确率 / 健康检查通过。凡是"报告质量好不好""规划合理不合理"这类主观判据，分数就交给了评委心情。

### 1.2 OS 味道：这是 OS 赛，不是 AI 应用赛

- 【事实】GitLink 赛题页联系人：纪斌（国防科大 jibin@nudt.edu.cn）、涂宏魁、刘美燕（麒麟 liumeiyan@kylinos.cn）；2026 版赛题维护：武汉大学蔡朝晖（zhcai@whu.edu.cn）。评审圈是 OS/国产平台背景，不是 AI 会议背景。
- 【判断】差异化加分点（按性价比排序）：
  1. **把多智能体系统讲成 OS**：智能体=进程、消息总线=IPC、DAG 调度器=进程调度器、接口契约=ABI、SharedWorkspace=文件系统。文档按这个叙事写。
  2. **调度策略对比实验**：AIOS 内置 FIFO / Round Robin（论文附录 D），我们做"不同调度策略下的端到端时间对比"——直接呼应 AIOS 论文，是最"懂 OS"的实验。
  3. **eBPF 可选叠加**（见 §3，历届一等奖热门技术）。
  4. **在 openKylin/银河麒麟上跑演示或声明兼容**——赛题明写"麒麟软件可提供软件开发环境"，联系人含麒麟员工，成本小印象分大。

### 4.1 C5「Medic」系统速写

**任务**：在受控 Linux（容器/虚拟机，可选 openKylin）中注入 N 类真实故障——内存泄漏进程、磁盘写满、CPU 饥饿/死锁、关键服务崩溃、网络丢包、配置错误、IO hang 等；多智能体系统自动完成"检测 → 诊断 → 修复 → 验证 → 报告"。

**智能体（6 类）**：
1. **指挥官 Planner**：分解诊断计划，按源分发分析任务，接收异常上报并重规划
2. **日志分析 Agent**（journalctl/dmesg）
3. **指标分析 Agent**（sar/proc/自定义探针）
4. **进程/资源分析 Agent**（top/ps/proc 快照）
5. **根因综合 Agent**：聚合多源证据 → 定位故障类目+组件+置信度；对低置信证据质询回源 Agent 补采
6. **修复 Agent + 验证 Agent**：受控白名单动作（kill/重启/清理/回滚配置），验证失败回环修复（双向），全部通过后由**报告 Agent** 出人话报告（可与验证并行起草）

**对照赛题要求**：≥4 种智能体（6 类）✅；≥4 并行子任务（日志/指标/进程/网络 4 路分析并行 + 报告）✅；双向交互 ≥3 对（实际 5 对：指挥↔分析补采、综合↔分析质询、修复↔验证回环、综合↔修复否决、指挥↔全体重规划）✅；依赖链 采集→分析→综合→修复→验证→报告 分层清晰 ✅。

**正确性协议（50 分的答案）**：注入 20 个已知故障用例，指标 = 根因定位准确率 + 恢复成功率 + 误报率，可复现、可出表出图。
**提速实验（50 分的答案）**：串行（逐源采集→逐源分析→综合）vs 并发（4 源并行分析 + vLLM 批处理），同构基线协议。
**7B 适配**：每个分析 Agent 只看单一源的裁剪片段，输出 JSON 诊断单（异常/证据/置信度）；确定性特征签名库兜底解析（已知故障的 grep 规则），LLM 负责泛化与综合——同样的"确定性工作不交给 LLM"原则。
**OS 叠加项**：故障注入器与健康探针是纯系统工程；可选 eBPF 采集器（一等奖热门技术）；openKylin 演示（麒麟支持方）。

### 4.2 C5 的风险与对策

| 风险 | 对策 |
|---|---|
| 修复动作的安全顾虑 | 全部在容器/VM 沙箱内执行白名单动作，文档明示 |
| 7B 误诊 | 签名库兜底 + 多源证据置信度加权 + 综合质询回环 |
| 注入器/探针工作量大 | 注入器=脚本集（每故障 20-50 行），M1 先做 5 类核心故障 |
| 演示比"生成软件"不直观 | 【判断】恰恰相反："现场注入故障→大屏看多智能体并行抢修→系统恢复+报告"的演示冲击力强于"生成一个小工具" |

## 5. 若切换场景，现有资产的复用度
