# 系统设计方案：DevForge —— 基于多智能体协作的模块化软件自动化开发系统

> 版本 v0.1（构思稿，2026-10-26）。对应赛题：智能体操作系统中的多智能体协作技术（2026 OS 设计赛·中西部与华南区域赛·功能挑战赛道）。
> 技术栈锚点：Linux + AIOS Kernel（agiresearch/AIOS）+ Cerebrum SDK（agiresearch/Cerebrum）+ 端侧 Qwen2.5-7B-Instruct（vLLM 接入），依据见 `note/research/aios-调研.md`。

## 1. 任务场景选择：为什么是"软件开发流水线"

赛题要求"自行拟定单智能体无法完成的复杂任务"。选 **软件自动化开发**，理由按评分点反推：

| 评分点 | 软件开发场景的优势 |
|---|---|
| 任务合理性（40分） | 一个含 4+ 功能模块的命令行应用，单次上下文喂给 7B 模型必然超长、模块间接口漂移、无法自证正确——"超出单智能体能力范围"天然成立，且是 AIOS 论文所属社区（SWE-agent/MetaGPT 等）公认的多智能体经典场景 |
| 并行子任务（赛题要求≥4） | 4 个功能模块的编码 + 文档编写天然可并行，无需生造 |
| 依赖约束（赛题要求） | "接口契约先行、实现依赖契约、测试依赖实现、集成依赖全部模块"是真实存在的工程依赖，DAG 不是摆设 |
| 正确性可客观验证（50分） | **pytest 单测 + 集成测试通过率、最终程序按需求可运行**，正确性不靠评委主观判断 |
| 提速可量化（50分） | 4 个模块并行生成 vs 串行逐个生成，配合 vLLM continuous batching，提速空间远超 20% 下限 |
| 7B 模型能力边界 | 模块被约束成"按契约实现若干函数"的小任务，Qwen2.5-7B/Coder-7B 可胜任；避开通放式长文生成 |

备选场景（若实测 7B 代码质量不达标时降级切换，见 §9）：**多领域行业研究简报编辑部**（主编/领域分析师×4/事实核查/数据校对/统稿编辑），纯文本流水线，7B 可靠性更高，但正确性偏主观。

**演示任务示例**（正式版准备 3 个不同规格的任务轮换演示）：
- 任务 A：学生成绩管理系统（CLI）：成绩录入/解析、统计报表、排名与预警、数据导出 4 模块
- 任务 B：记账工具：交易解析、月度汇总、预算检查、报表生成 4 模块
- 任务 C：文本语料处理工具：分词统计、关键词提取、格式转换、报告生成 4 模块

输入：一份自然语言需求文档（PRD）+ 每模块的函数签名级契约模板。

## 2. 智能体角色设计（6 类，满足"不少于 4 种"）

每个智能体是一个符合 Cerebrum SDK 规范的独立智能体包（`entry.py + config.json + meta_requirements.txt`）：

| # | 智能体 | 职责 | 输入 → 输出 |
|---|---|---|---|
| 1 | **Planner 规划师** | 解析 PRD，分解任务，产出带依赖关系的子任务 DAG；执行中接收进度与异常，做重规划 | PRD → 任务 DAG（JSON） |
| 2 | **Architect 架构师** | 与 Planner 双向澄清需求后，定义模块划分、数据结构与**接口契约**（函数签名 + 类型 + 约定） | DAG + PRD → contract.json |
| 3 | **Coder 程序员**（多实例） | 按契约实现单个模块的代码；接收 Tester 的失败报告与 Reviewer 的审查意见，修复后重新提交 | 契约 + 审查/测试反馈 → module_i.py |
| 4 | **Tester 测试工程师**（多实例） | 按契约为模块生成 pytest 用例，**本地实际运行**测试，把失败堆栈回传给对应 Coder | 契约 → test_module_i.py + 测试报告 |
| 5 | **Reviewer 审查员** | 审查代码与契约一致性、风格、隐患；不通过则附意见打回 Coder，通过则签署放行 | 模块代码 → 审查意见 |
| 6 | **DocWriter 文档工程师** | 依赖契约（而非实现）并行编写 README 与用户手册；集成后补充安装/运行说明 | 契约 + 最终结构 → README.md |

集成工作（把通过审查的模块拼成可运行工程、跑集成测试）由 Architect 二次担任（契约的维护者做集成最顺），不新增角色。

## 3. 协作流程（DAG + 回环）

```
PRD
 └─> Planner ──澄清问答(双向)──> Architect ──> contract.json
                                    │
        ┌───────────┬───────────┬───┴───────┬───────────┐
        v           v           v           v           v
    Coder#1     Coder#2     Coder#3     Coder#4     DocWriter     ← 并行层
        v           v           v           v
    Tester#1    Tester#2    Tester#3    Tester#4                   ← 并行层
        ^           ^           ^           ^
        └─失败堆栈回传(双向)──各自 Coder──审查意见(双向)──┐
                                                    v
                                                Reviewer     ← 逐模块审查
                                                    │ 全部放行
                                                    v
                                        Architect: 集成 + 集成测试
                                                    │ 失败→定位回传对应 Coder(双向)
                                                    v
                                        交付物: 代码+测试+文档+执行报告
```

- **并行子任务**：4 个模块的"编码→测试"链 + 1 条文档链，共 5 路并行（满足 ≥4）。
- **依赖与顺序约束**：Planner→Architect→并行层→Reviewer→集成，串行骨架清晰；并行层内部互不依赖。
- **双向交互对（满足 ≥3 对，实配 5 对）**：
  1. Planner ↔ Architect：需求澄清问答
  2. Coder ↔ Tester：失败堆栈回传 → 修复 → 重测（最多 N 轮，超限上报 Planner）
  3. Coder ↔ Reviewer：审查意见 → 修订 → 复审
  4. Architect ↔ Coder：接口歧义澄清；集成失败定位回传
  5. Planner ↔ 全体：进度/异常上报与重规划
- **容错**：单模块修复超限（默认 3 轮）→ Planner 收窄该模块契约或降级该模块功能，不阻塞其余模块交付。

## 4. 关键机制设计

### 4.1 协作中间件（自建，跑在 AIOS 之上）

Cerebrum SDK 的智能体间通信与编排能力待克隆源码确认（见调研笔记 §7），因此设计一个自研的轻量协作层作为兜底，同时在"操作系统"语境下构成加分点：

- **MessageBus**：发布/订阅式消息路由，每条消息带 `(from_agent, to_agent, type, payload, round)`；所有智能体间交互走总线并落盘日志（供回放与演示）。
- **DAGScheduler**：按 DAG 拓扑就绪一个调度一个，就绪的子任务并发派发；子任务完成事件驱动下游；这是"考虑并满足执行先后顺序及依赖关系"的直接实现。
- **SharedWorkspace**：基于 AIOS Storage Manager 的共享文件区（契约、代码、测试报告、审查意见、版本），智能体不直接对话传递大文件，只传引用，控制 7B 的上下文长度。

> 若克隆后发现 SDK 原生具备消息路由/工作流能力，则优先用原生能力，MessageBus 退化为薄封装；最终以哪条路线落地，在 M1 结束时定版。

### 4.2 7B 模型可靠性工程（本方案成败关键）

- **单一职责小提示词**：每个智能体的 system prompt 只描述一件事；对话历史裁剪为"最近 2 轮 + 契约摘要"。
- **结构化输出强约束**：所有智能体间消息用 JSON Schema 约束（函数式工具调用格式输出），解析失败自动重试（≤2 次），重试仍失败则走默认模板兜底。
- **模板脚手架**：Coder 收到的是"契约 + 代码骨架模板 + 风格示例"，把自由生成收敛为填空式生成。
- **温度 0~0.2**；Planner/Architect 阶段可到 0.4。
- **确定性工作不交给 LLM**：pytest 运行、文件读写、DAG 计算全部是确定性代码；LLM 只做生成/审查/澄清。

### 4.3 性能对比实验设计（"并发比串行快 ≥20%"）

- **同构对比**：完全相同的 6 类智能体、相同 PRD、相同模型与参数，仅调度方式不同：
  - 串行基线：按拓扑序逐个执行智能体调用，前一个结束下一个才开始；
  - 并发方案：DAGScheduler 就绪即派发，vLLM continuous batching 吞并发请求。
- 指标：端到端墙钟时间、各阶段时间分解（LLM 推理 / 工具执行 / 等待）、LLM 并发度曲线。
- 规模：3 个演示任务 × 每种调度 × 3 次重复，取均值与方差，出图表。
- 理论预期：串行 ≈ Σ各阶段；并发 ≈ 关键路径 + 合流开销。4 路并行编码层占大头时，即便 vLLM 批处理有排队损耗，总时间也应降 40%+（论文同路线实验为最高 2.1x，本指标只要求 20%）。
- 诚实性红线：串行基线不得人为弱化（不用更差参数、不加人为延迟），文档中写明两种模式的完整配置。

## 7. 风险与对策

| 风险 | 概率 | 对策 |
|---|---|---|
| Cerebrum SDK 智能体通信/编排能力不足或文档缺失 | 中 | M1 第一周即克隆源码摸底；自建 MessageBus+DAGScheduler 兜底（§4.1） |
| 7B 代码质量不达标导致正确性翻车 | 中 | 契约模板收敛生成空间；超限降级机制；极端时整体切换备选场景（编辑部） |
| AIOS Kernel 与 vLLM 版本兼容问题 | 低-中 | 锁定 Python 3.10/3.11 与 requirements 版本；问题及时向赛题维护人（武汉大学 蔡朝晖 zhcai@whu.edu.cn）或官方渠道咨询 |
| 提速不足 20% | 低 | 保证并行层任务量占端到端 ≥60%；必要时加深任务规模（更多模块） |
| 时间不够（截止 12-27） | 中 | 计划留 2 周缓冲；M2 结束时若核心链路未跑通，立即收缩为 4 智能体最小闭环 |

## 8. 里程碑验收标准

- **M1**：环境跑通 `run-agent` 官方示例；摸清 SDK 通信/编排能力并定路线；架构定版（本文档 v1.0）
- **M2**：单任务（成绩管理系统）在并发模式下端到端跑通，pytest 通过
- **M3**：串行/并发对比实验出数，提速 ≥20%，3 任务稳定复现
- **M4**：文档、演示材料、复现包齐备，提交

## 9. 备选方案速览（降级路线）

**多领域行业研究简报编辑部**：主编（分解选题）→ 4 个领域分析师（基于本地语料并行写分节）→ 事实核查员（比对原文，双向打回）→ 数据校对员（核对数字引用）→ 统稿编辑（汇总+风格统一）。双向交互与 DAG 结构同构，纯文本任务对 7B 更友好；正确性验证退化为"引用可溯源 + 核查通过率"，弱于 pytest，故仅作降级。触发条件见 §7。
