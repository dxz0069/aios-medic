## 1. 任务场景与合理性论证

**任务定义**：在受控 Linux 环境（容器/虚拟机，兼容 openKylin）中注入系统故障，多智能体系统自动完成"检测 → 并行诊断 → 根因定位 → 受控修复 → 验证 → 报告"的全流程，输出人话诊断报告与恢复证明。

**为什么"合理"（对应 40 分）**：
1. **单智能体不可行，且有对照实验**：一次故障的判据散落在日志、指标、进程快照、网络状态四个信息源，合并后超出 7B 上下文与注意力能力——对照实验将把全部原始信息一次性喂给单智能体，展示其定位失败/遗漏/幻觉，与 Medic 的成功形成对比；
2. **现实意义**：系统故障诊断与自愈（AIOps）是 OS 运维真实痛点；全国功能赛道 2025 年一等奖已有"基于 LLM 的 kdump 分析"先例（哈工深），方向受评委认可（见选题决策文档 §3）；
3. **分解与依赖是内在的**：多源并行分析→证据综合→修复→验证的依赖链是诊断业务本身的结构，非生造。

## 2. 系统总体架构

```
┌────────────────────────── 受控实验床（容器/VM，可选 openKylin）──────────────────────────┐
│  FaultInjector 故障注入器（脚本集）   HealthProbes 健康探针   确定性特征签名库              │
└───────────────▲──────────────────────────────▲──────────────────────────────┬──────────┘
                │ 采集命令/文件                 │ 水位/状态                     │
┌───────────────┴──────────────────────────────┴──────────────────────────────▼──────────┐
│                        AIOS Kernel（LLM/内存/存储/工具/调度，launch_kernel.sh）           │
├────────────────────────────────────────────────────────────────────────────────────────┤
│  协作中间件（自研，跑在 Cerebrum SDK 之上）                                              │
│  MessageBus（pub/sub，全消息落盘）  DAGScheduler（就绪即派发）  SharedWorkspace（文件区） │
├────────────────────────────────────────────────────────────────────────────────────────┤
│  智能体层（Cerebrum SDK 规范，9 类角色）                                                 │
│  Commander / LogAnalyst / MetricAnalyst / ProcAnalyst / NetAnalyst /                    │
│  Diagnostician / Repairer / Verifier / Reporter                                         │
└────────────────────────────────────────────────────────────────────────────────────────┘
```

- 智能体=进程、MessageBus=IPC、DAGScheduler=进程调度器、接口契约/消息 Schema=ABI、SharedWorkspace=文件系统——全文按此 OS 叙事撰写（差异化策略，见选题决策文档 §1.2）。
- 采集/探针/注入器为确定性代码（普通工具 + 脚本），LLM 只做分析、综合与报告——延续"确定性工作不交给 LLM"原则。
- 若克隆 Cerebrum 后发现原生消息路由/工作流能力可用，MessageBus/DAGScheduler 退化为薄封装（M0 定版）。

## 3. 智能体设计（9 类，满足"≥4 种"）

| # | 角色 | 职责 | 输入 → 输出 |
|---|---|---|---|
| 1 | **Commander 指挥官** | 接收异常告警，生成诊断计划（DAG），按源分发；接收异常/超限上报并重规划 | 告警 + 实验床上下文 → 诊断计划 JSON |
| 2 | **LogAnalyst 日志分析** | 裁剪 journalctl/dmesg 片段，抽取异常事件，输出诊断单 | 日志片段 → 诊断单 JSON |
| 3 | **MetricAnalyst 指标分析** | sar/proc 时序水位（CPU/内存/磁盘/IO），判异常区间 | 指标片段 → 诊断单 JSON |
| 4 | **ProcAnalyst 进程分析** | ps/top/proc 快照，找泄漏/僵尸/句柄异常进程 | 进程快照 → 诊断单 JSON |
| 5 | **NetAnalyst 网络分析** | ss/ping/tc 规则，判丢包/延迟/端口异常 | 网络状态 → 诊断单 JSON |
| 6 | **Diagnostician 根因综合** | 聚合多源诊断单 → 根因类目+组件+置信度；低置信则质询对应分析智能体补采；产出修复方案 | 诊断单集合 → 根因结论 JSON |
| 7 | **Repairer 修复执行** | 在白名单内执行修复动作（kill/重启服务/清理/回滚配置/删 tc 规则） | 修复方案 → 动作日志 |
| 8 | **Verifier 验证** | 跑健康探针判定是否恢复；失败回传 Repairer（回环） | 探针结果 → 验证结论 |
| 9 | **Reporter 报告** | 与验证并行起草诊断报告（现象/证据链/根因/动作/预防建议） | 全部工件 → report.md |

说明：四个分析智能体共享同一基类，按"源特化提示词 + 专用采集工具 + 输出 Schema"实例化为 4 种不同类型智能体；各自独立打包为 Cerebrum 智能体（entry.py + config.json）。

## 4. 协作流程（DAG + 回环）

```
异常告警（探针触发 / 外部注入通知）
   └→ Commander 生成诊断计划
        ├─并行─→ LogAnalyst ──诊断单──┐
        ├─并行─→ MetricAnalyst ───────┤
        ├─并行─→ ProcAnalyst ─────────┤          ← 4 路并行分析（可并行子任务）
        └─并行─→ NetAnalyst ──────────┘
             ↑补采请求①                ↓
        Diagnostician ←────质询②────────（低置信证据回源补采）
             ↓ 修复方案      ↑方案否决③
        Repairer ──执行──→ Verifier ──失败回环④──→ Repairer
                                  └─通过─→ 交付
        Reporter ∥（诊断结论一出即并行起草，验证结论补录）
   交付物：report.md + 修复动作日志 + 恢复证明 + 全程消息回放
```

**双向交互对（5 对，满足"≥3 对"）**：
1. Commander ↔ 分析智能体：分发诊断任务 / 补采请求与异常上报
2. Diagnostician ↔ 分析智能体：质询低置信证据 / 补采结果回传
3. Diagnostician ↔ Repairer：修复方案下发 / 方案不可行否决与调整
4. Repairer ↔ Verifier：修复动作执行 / 验证失败回环（默认最多 3 轮，超限上报 Commander 重规划）
5. Commander ↔ 全体：进度上报 / 重规划指令

**依赖与顺序约束**：告警→计划→（并行分析）→综合→修复→验证→交付，层次分明；并行层内互不依赖；报告链与验证链部分重叠。

**消息 Schema 示例**（全部消息走 MessageBus 落盘）：

```json
{
  "msg_id": "uuid", "from": "Diagnostician", "to": "LogAnalyst",
  "type": "EVIDENCE_CHALLENGE", "round": 2, "ts": "ISO8601",
  "payload": { "ref": "diag-001", "question": "OOM killer 事件的确切时间戳与受害进程", "deadline_s": 30 }
}
```

## 5. 受控实验床

- **故障目录**（20 用例，每例 = 注入脚本 + 根因金标签 + 恢复判据）：
  - 首批 5 类核心（M1）：内存泄漏进程（自写 leaky 程序）、磁盘写满（dd 填充）、CPU 饱和饥饿（stress-ng）、关键服务崩溃（反复退出的 systemd 玩具服务）、网络丢包延迟（tc netem）
  - 扩展 15 例（M2）：僵尸进程堆积、文件句柄耗尽、inode 耗尽、配置错误（坏 yaml/错端口）、日志风暴、OOM kill 事件、DNS 解析失败、权限错误、IO 高延迟、swap 耗尽、进程死锁、服务依赖环、端口占用冲突、时钟跳变、tc 高延迟变体
- **修复动作白名单**（仅在沙箱内执行）：kill 指定 PID、systemctl restart 指定服务、删除指定临时大文件、从备份回滚指定配置、删除 tc netem 规则；白名单外动作一律拒绝并记录。
- **安全边界**：全部在一次性容器/VM 内进行，宿主机只读采集。

## 6. 7B 可靠性工程

1. 单一职责小提示词：每个分析智能体只看单源裁剪片段（≤2K token）；
2. 结构化输出：诊断单 JSON Schema（异常事件/证据/置信度/建议补采项），解析失败重试 ≤2 次，仍失败用签名库确定性解析兜底；
3. 确定性特征签名库：每类故障预置 grep/阈值规则，保证正确性下限；LLM 负责泛化、综合与人话报告；
4. 置信度加权聚合：Diagnostician 按源可靠度与置信度加权，低于阈值触发质询回环；
5. 温度 0~0.2（Diagnostician/Reporter 可 0.4）。

## 7. 正确性验收协议（对应 50 分）

- 指标：**根因定位准确率**（结论类目+组件与金标签一致）、**恢复成功率**（健康探针全绿）、**误报率**（无故障空跑用例中的虚警）；辅助：证据链完整性（报告引用的证据可回溯到原始采集文件）。
- 规模：20 用例 × 3 次重复；输出正确性报告（表格 + 混淆矩阵）。
- 单智能体对照实验（§1）同场输出，一并写入报告。

## 8. 性能对比协议（对应 50 分）

- **同构基线**：同一套智能体、提示词、参数与实验床，串行模式按 DAG 拓扑序逐个执行（前一个结束下一个才开始）；并发模式 DAGScheduler 就绪即派发 + vLLM continuous batching。两组配置除调度外完全一致，脚本化可复现。
- 指标：端到端墙钟时间、阶段分解（采集/LLM 推理/工具执行/等待）、LLM 并发度曲线。
- 规模：20 用例 × 2 模式 × 3 重复，取均值与方差出图。
- 附加实验（OS 加分）：AIOS 内置调度策略（FIFO / Round Robin）下的端到端时间对比，呼应 AIOS 论文（见调研笔记 §2 修正）。
- 目标：总时间减少 ≥20%（赛题底线），预期 40%+（并行分析层占端到端 ≥60%）。

## 11. 风险与对策

| 风险 | 概率 | 对策 |
|---|---|---|
| 7B 诊断单输出不稳 | 中 | M0 spike 先测 20 条样本；签名库兜底；失败率 >30% 触发 §12 kill-switch |
