## 2. 目标与获奖策略

- 硬指标（评分 200 分制映射）：
  - 功能完整性 50%：任务场景合理性（40）+ 多智能体实现与协作流程（60）→ 靠设计方案（见 `note/design/系统设计方案.md`）
  - 应用效果 50%：并发比串行提速 ≥20%（50）+ 正确完成任务（50）→ 靠实验与 pytest 客观验证
- 策略：选"正确性可客观验证"的软件开发场景，把两项 50 分的应用效果分做实；用自建协作中间件（MessageBus + DAGScheduler）体现"操作系统"深度，区别于纯 prompt 串接的队伍。
- 硬件需求：1 台 Linux + 1 张 ≥24GB 显存 GPU（跑 Qwen2.5-7B + vLLM；4090/A6000/租用云 GPU 均可），无 GPU 时用 ollama 降级开发。

## 3. 里程碑与周计划

### M0 准备（10-26 → 11-01，第 1 周）
- 确认报名、通读章程与提交要求（队长）
- 环境：Ubuntu + Python 3.10/3.11 虚拟环境；克隆并安装 AIOS Kernel 与 Cerebrum SDK；拉起 `runtime/launch_kernel.sh`
- 模型：`vllm serve` 跑通 Qwen2.5-7B-Instruct，config.yaml 接入，`aios env list` 可见
- 用 `run-agent` 跑通一个官方示例智能体（冒烟）
- **摸底（关键）**：读 `cerebrum/example/` 与源码，回答调研笔记 §7 的 5 个待确认问题，决定"原生通信 vs 自建中间件"路线
- 验收：示例智能体经 Kernel 调用本地 7B 成功返回；路线决定记入设计文档 v1.0

### M1 核心链路（11-02 → 11-15，第 2-3 周）
- 实现协作中间件骨架：MessageBus（pub/sub + 落盘日志）、DAGScheduler（就绪即派发）、SharedWorkspace
- 实现 Planner、Architect：PRD → DAG JSON → contract.json（结构化输出 + 校验重试）
- 实现 Coder、Tester 单模块闭环：1 个模块"实现→测试→失败回传→修复"跑通
- 验收：任务 A（成绩管理系统）单模块链路端到端跑通，pytest 通过

### M2 全系统并发闭环（11-16 → 11-29，第 4-5 周）
- Reviewer、DocWriter 补齐；4 模块 + 文档 5 路并行全流程跑通
- 串行调度器（同构基线，按拓扑序逐个执行）
- 容错：修复超限上报与降级、集成失败定位回传
- 三任务（A/B/C）稳定复现，正确性报告（测试通过率）成形
- 验收：并发模式端到端正确完成 3 个任务；**若 11-29 未达成，立即收缩为 4 智能体最小闭环并冻结功能范围**（风险预案 §5）

### M3 性能实验（11-30 → 12-06，第 6 周）
- 3 任务 × 2 调度模式 × 3 次重复，统计墙钟时间与阶段分解
- 出图：甘特/时间线对比、并发度曲线、提速百分比
- 若提速 <20%：增大并行层任务占比/模块数，排查串行化瓶颈（vLLM 排队、总线锁）
- 验收：提速 ≥20% 有数据、有图、有方差；实验方法写入文档

### M4 文档与提交（12-07 → 12-20，第 7-8 周）
- 设计实现文档（架构图、消息 Schema、调度算法、实验方法与结果、复现步骤）
- 演示材料：终端回放 + 执行时间线可视化
- 一键复现包：环境脚本 + 模型下载启动脚本
- 内部评审一轮（交叉验收：换人按文档复现）
- **12-20 前提交到中西部与华南区域赛平台**，12-21~27 仅做提交问题应急

### 缓冲（12-21 → 12-27）
- 应对平台提交异常、材料补正；不做新功能

## 5. 风险预案（摘要，详表见设计方案 §7）

1. SDK 能力不足 → 自建中间件路线已内建（M0 定夺）
2. 7B 代码质量不达标 → 契约模板收敛 + 超限降级；极端时切备选场景"编辑部"（设计方案 §9）
3. 11-29 核心链路未通 → 冻结范围，保 4 智能体最小闭环参赛
4. 提速不达标 → 加大并行层任务量、排查串行化点（M3 专周处理）
5. 环境兼容问题 → 锁版本；必要时邮件咨询赛题维护人
