## 2. 目标与获奖策略

- 评分结构（200 分）：任务合理 40 + 协作流程 60（最大单项，逐条对照赛题四要求留证据）+ 提速 ≥20% 50 + 正确完成 50。
- 策略（依据选题决策文档）：
  1. **正确性机器可判**：20 个注入故障用例的定位准确率/恢复成功率/误报率；
  2. **提速协议同构可复现**：串行基线与并发版仅调度不同，防"刷分"质疑；
  3. **OS 叙事差异化**：智能体=进程/总线=IPC/DAG 调度器=调度器；叠加 AIOS 调度策略（FIFO/RR）对比实验；
  4. **评委对味**：方向对齐 2025 一等奖"LLM kdump 分析"先例；可选 eBPF 采集器、openKylin 演示（麒麟为赛题支持方）。
- 硬件：1 台 Linux + 1 张 ≥24GB 显存 GPU（vLLM 跑 Qwen2.5-7B；论文先例即单卡 A5000 24GB 跑 8B）；无 GPU 时用 ollama 降级开发。

## 3. 里程碑与周计划

### M0 环境 + 定版（11-11 → 11-15，本周）
- 确认报名；登录 educg 核实提交材料清单与评审方式，回填 §1
- 环境：Ubuntu + Python 3.10/3.11；克隆安装 AIOS Kernel 与 Cerebrum SDK，`launch_kernel.sh` 拉起；vLLM 跑通 Qwen2.5-7B，config.yaml 接入
- **Spike ①（kill-switch 项）**：7B 对 20 条单源日志/指标片段输出 JSON 诊断单，统计成功率（>70% 通过，≤30% 触发回退 DevForge）
- **Spike ②**：`run-agent` 跑通官方示例智能体；摸清 Cerebrum 通信/编排能力，定"原生 vs 自建中间件"路线（回答调研笔记 §7 五问）
- **Spike ③**：故障注入器原型（内存泄漏/磁盘满/CPU 饱和/服务崩溃/tc 丢包 5 类脚本）+ 健康探针
- 验收：三项 spike 有结论；设计文档 v1.0（场景章定稿）

### M1 核心链路（11-16 → 11-29，第 2-3 周）
- 协作中间件骨架：MessageBus（pub/sub + 落盘）、DAGScheduler（就绪即派发）、SharedWorkspace
- 4 个分析智能体 + Commander + Diagnostician；单故障用例闭环：注入 → 并行采集分析 → 综合定位（与金标签比对）
- 串行调度器（同构基线，按拓扑序逐个执行）
- 验收：5 类核心故障并发模式端到端定位成功；**11-29 若未达成，收缩为"诊断-only"闭环（去掉修复链）保底参赛**

### M2 全系统 + 正确性（11-30 → 12-06，第 4 周）
- Repairer + Verifier（白名单动作 + 回环）+ Reporter 补齐；修复-验证-报告全流程
- 故障目录扩到 20 用例；正确性实验：20 用例 × 3 次，出定位准确率/恢复成功率/误报率与混淆矩阵
- 单智能体对照实验（整任务一次喂给单 agent，记录失败模式）
- 验收：20 用例数据齐；恢复成功率与定位准确率达内部目标（≥80%/≥85%，实测后校准）

### M3 性能实验（12-07 → 12-13，第 5 周）
- 20 用例 × 串行/并发 × 3 次重复：端到端墙钟、阶段分解、并发度曲线
- AIOS 调度策略（FIFO/RR）对比实验
- 若提速 <20%：加大并行层占比、排查 vLLM 排队与总线串行点
- 验收：提速 ≥20% 有数据有图有方差；写入实验报告（`note/report/perf/`）

### M4 文档与提交（12-14 → 12-20，第 6 周）
- 设计实现文档（架构/消息 Schema/调度算法/两份协议与结果/复现步骤）
- 演示材料：现场注入故障演示脚本 + 终端回放 + 时间线可视化 + 对比图
- 一键复现包；内部交叉验收（换人按文档复现）
- **12-20 前提交**（源代码 + 设计实现文档，材料清单以平台为准）

### 缓冲（12-21 → 12-27）
- 平台提交异常与材料补正应急；不加新功能

## 5. 风险预案（摘要，详表见设计方案 §11）

1. Spike ① 失败率 >30%（11-15）⇒ 回退 DevForge（设计方案附录 A，设计资产零沉没）
2. SDK 能力不足 ⇒ 自建中间件路线已内建
3. 11-29 核心链路未通 ⇒ 冻结为诊断-only 最小闭环
4. 提速不达标 ⇒ M3 专周排查（并行层占比/批处理/串行点）
5. 环境兼容 ⇒ 锁版本，邮件咨询维护人
